# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core, so each query is written once for both databases. It uses Supabase (Postgres) when `DATABASE_URL` is in its environment, in a schema of its own, `undercover`, and otherwise SQLite. `npm run dev` passes `.env`; the tests never do. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. Supabase's free plan allows 15 connections through the session pooler, so each process uses at most 4, and a request waits up to 120 seconds for one rather than fail. At most 8 requests are inside the backend at once (`backend/turns.py`); the rest wait on the event loop, so a swarm can't take every worker thread while the requests holding the connections wait for one.
  - Sign-in: every handler action takes a Supabase access token, which `backend/auth.py` checks with PyJWT's `PyJWKClient` against the project's public keys at `/auth/v1/.well-known/jwks.json` under `VITE_SUPABASE_URL` (read once), with the audience `authenticated`, then finds the handler by the token's email. The project signs with asymmetric keys, so no Supabase secret is needed. The agent's own calls carry `UNDERCOVER_API_KEY` in an `X-API-Key` header, checked in `backend/keys.py` with `secrets.compare_digest` and read from the request rather than with `Header()`, so no API document shows a key input. `agent/client.py` sends it on every call.
  - The agent's own API (`backend/agent_api.py`): `GET /api/agent/openapi.json`, generated with FastAPI's `get_openapi` from the app's routes, filtered to the claim agent's six operations, with no `servers`, for the AgentCore Gateway.
  - Seeding reads `context/plans.yaml` into the plans table and the two documents into the documents table, with PyYAML. The app reads `context/` at no other time. Section 14's checks on a decision are in `backend/decision_record.py`, with messages of our own.
  - The configuration's versions, the recipe's versions, the settings and the rounds are records the backend owns. Diffs are worked out with Python's `difflib`, and our rule for keeping a version is `backend/verdict.py`.
  - The judge (`backend/judge.py`): Jev, `typesafe/jev-1.13`, through OpenRouter's Decisions endpoint with the `openrouter` package, called only there, at the origin in `JUDGE_URL` (read once; `https://openrouter.ai` by default), with a 10-second timeout and no retries. It runs in the backend, which holds the handlers' reasons, as an evaluation finishes, every claim in parallel.
- `context/`: the context layer, an MCP server from the `mcp` package's FastMCP, stateless with JSON responses at `/mcp`, with seven read-only tools over data governance's files, which it reads once when it starts. `uv run -m context` serves it on port 8006 with uvicorn; on Lambda, `context.server.handler` builds a fresh server for each request under Mangum.
- `agent/`: our own harness on OpenRouter, in six parts. The improver is a LangChain agent; the rest is our own LangGraph code:
  - The security check (`agent/screening.py`): the claim graph's first node, `check`, a call to GPT-6 Luna at effort `none` with Structured Outputs (`instructions_found` and the reason) through the OpenRouter SDK, on the fields the customer wrote. It isn't part of the versioned configuration.
  - The dispatcher (`agent/dispatcher.py`), a LangGraph graph with no model, as in the Week 2 Day 4 lab: a node lists the run's claims and fans out with one `Send` per claim to a worker node, with `max_concurrency` set to N. It works dispatches and evaluations. The worker calls one function of the harness, `claim.work(claim_id, run)`, and is the only place the dispatcher touches the claim agent. Its `RetryPolicy` waits out LangChain's `ModelRateLimitError` and `ModelTimeoutError`; on the last attempt the worker leaves the claim in progress, which is the `error_handler`'s job, because in LangGraph 1.2.12 an `error_handler` doesn't stop the error while other `Send` tasks run beside it. It saves no progress of its own.
  - The claim agent, a hand-written LangGraph graph, works a claim on a thread of its own. Its nodes record each step and each reply's tokens and cost, return refusals to the model and stop at 30 model calls. It pays as a step of the graph, and waits for a sign-off with `interrupt()` when the backend says a claim needs one. `claim.work` carries on a claim in progress or starts a waiting one, lets rate limits and timeouts through to the dispatcher, and times each run of the graph, which ends at a pause for a sign-off.
  - Its progress is saved after every step with LangGraph's synchronous Postgres checkpointer, in the same database, with `durability="sync"`. Each run of the graph gets a saver of its own on the process's shared pool of 4 connections, because a saver holds a lock around every read and write.
  - The agent's AgentCore app (`agent/entrypoint.py`), the agent's entry point: `BedrockAgentCoreApp` from `bedrock-agentcore`, with one entrypoint that takes a payload naming an operation (`health`, `work_run`, `work_round`, `carry_round_on`, `stop_round`, `work_claim`, `resume_claim`), checked with pydantic. It answers at once, then does the work on a thread of its own, registered as an async task so `/ping` says `HealthyBusy` while it goes. It gets ready on its first request (`agent/ready.py`), and off Runtime it needs `Authorization: Bearer <UNDERCOVER_API_KEY>` for all but the health check. The app creates the runs, rounds and reviews and decides what may start (`backend/work.py`: one dispatch, evaluation or working round at a time, with the `agent_work` row as its lock); the agent tells the app every minute while it works, and work it hasn't heard of for five minutes is stopped with "The agent stopped answering". The app reaches the agent through `backend/agent_service.py`: at `UNDERCOVER_AGENT` (`http://127.0.0.1:8080`) on the laptop, or with boto3's `invoke_agent_runtime` when `UNDERCOVER_AGENT_RUNTIME` is set. The agent reaches the app at `UNDERCOVER_API` (`http://127.0.0.1:8000`).
  - Tracing: each claim's work is one Langfuse session, named after its thread, tagged with its run, such as `dispatch-12`, and its round, such as `round-3`. The improver's work in a round is one session, named after the round's thread.
  - The improver (`agent/improver.py`): a LangChain `create_agent` on GPT-6 Luna at medium reasoning effort, with parallel tool calls turned off and at most 20 model calls a round, the lab's four tools, `HumanInTheLoopMiddleware` on its two proposals and a `PostgresSaver` of its own, on a new thread for each round. The agent works a round in `agent/rounds.py`: its evaluations through the dispatcher in this process, each in a fresh `contextvars.Context`. The app opens the round and records each review, and the agent carries the round on from the review's id; a round waiting for a review lets other work start.

  The claim agent's tools take one of two routes, chosen when its graph is built: with `UNDERCOVER_GATEWAY_URL` set, the AgentCore Gateway's MCP tools over streamable HTTP, signed with SigV4 for `bedrock-agentcore` (`agent/gateway.py`); otherwise the app with the key and the context layer at `UNDERCOVER_CONTEXT` unsigned (`agent/direct.py`). The `mcp` package's async client runs on a loop of its own (`agent/mcp_bridge.py`), so the agent stays synchronous. With `UNDERCOVER_MEMORY_ID` set, the claim graph's store is `AgentCoreMemoryStore` from `langgraph-checkpoint-aws` (`agent/memory.py`), reached directly with the AWS CLI's credentials. Its bookkeeping and its configuration go straight to the backend's API, with `agent/client.py`; the improver reaches its round, its results and its spending through `agent/improver_client.py`. Each run is built from a version of the configuration: its model and reasoning effort (`default` sets none), or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort set. With `MODEL_NAME` set, that model is the only one allowed, the improver uses it too, and the judge isn't called.
- `dashboard/`: React, Vite and TypeScript. Handlers sign in with `@supabase/supabase-js` and `signInWithPassword`, reading `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, only in `dashboard/src/auth.ts`. Vite reads the repo's `.env` for `npm run dev` only; the unit and end-to-end tests set their own values. The appearance, light, dark or as the computer is, is kept in the browser and set as `data-theme` on the page. Charts are SVG, with no chart library.
- `e2e/`: Playwright tests, with stand-ins for the agent's AgentCore app, Supabase Auth and the judge.
- `data/`: the business data the backend starts from: `company.json` gives the approval limit its first value, `settings.json` the improvement settings, and `models.json` the models the claim agent may use, with their reasoning efforts and prices per million tokens. `data/evals/` holds the answer key: seeding stores the held-out claims and the handlers' decisions, with their reasons and references, in tables of their own, which no claim operation reads. Only the scoring of an evaluation, the judge and the improver's view use them, and the improver's view holds nothing of the held-out set but its scores. The claim agent never sees them.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. In `.env`: `OPENROUTER_API_KEY`, `DATABASE_URL` (the Supabase session pooler string), `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, `HANDLER_PASSWORD`, the handlers' password for the browser checks, and `UNDERCOVER_API_KEY`, the agent's API key, made with `secrets.token_urlsafe(32)`. Once the deployment has made them: `UNDERCOVER_GATEWAY_URL`, `UNDERCOVER_MEMORY_ID`, and `UNDERCOVER_CONTEXT` for a context layer elsewhere than http://127.0.0.1:8006/mcp.

## Deployment

The backend and the dashboard go to AWS Lambda as one package behind a Function URL, with the database on Supabase. The same app also runs as an ordinary web server.

- `npm run build` builds the dashboard into `dashboard/dist`, with `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` built in, read from `.env` when there is one and otherwise from the environment.
- When `dashboard/dist` exists, the backend serves it at `/` (`backend/static.py`): its files at their own paths, and `index.html` for any other path outside `/api/`. Without it, the backend serves only the API, as with `npm run dev`.
- The package holds `backend/`, `data/` and `dashboard/dist/`, with the packages of the `server` dependency group in `pyproject.toml`, installed for Linux and Python 3.12. At run time the backend imports nothing from outside the package, reads only its own files and writes none. `npm run check:server` imports the backend with only that group installed, in a temporary environment.
- Lambda runs the handler `backend.main.handler`, Mangum with the startup hook off, so nothing seeds the database. A web server runs `backend.main:app`.
- The app reads `context/` only while seeding, never when it's imported or for a request, so its package needs no `context/`; a decision's manual version comes from the documents table.
- The function's environment is `DATABASE_URL` (Supabase's transaction pooler, on port 6543), `VITE_SUPABASE_URL` and `UNDERCOVER_API_KEY`. Everything else the backend reads has a default, or is needed only to reach the agent: `UNDERCOVER_AGENT_RUNTIME` on Lambda.
- When `AWS_LAMBDA_FUNCTION_NAME` is set, as Lambda sets it, the backend opens a database connection for each request and keeps none (`NullPool`), with prepared statements off (`prepare_threshold=None`), since each copy of the function handles one request at a time and the transaction pooler can't prepare statements.

### The agent on Runtime

- The AgentCore project in `agentcore/` deploys one runtime, `agent`, with `agentcore deploy`. Its package is `runtime/` with `agent/` beside it, without the tests, and the `runtime` group's packages at `uv.lock`'s versions, installed for Linux on ARM and Python 3.12. Runtime starts `runtime/main.py` in each session, and the file runs the agent's AgentCore app. The runtime's role may call the Gateway and use the Memory (`runtime/policy.json`). `npm run check:runtime` imports `runtime.main` with only that group installed, in a temporary environment.
- The agent's settings on Runtime: `OPENROUTER_API_KEY`, `UNDERCOVER_API_KEY` and `DATABASE_URL` (Supabase's transaction pooler, port 6543) are credentials in AgentCore Identity, which the agent fetches on its first request (any `AGENTCORE_CREDENTIAL_<NAME>_NAME` set means it's on Runtime); `UNDERCOVER_API`, `UNDERCOVER_GATEWAY_URL` and `UNDERCOVER_MEMORY_ID` come from `agentcore/.env.local` when `agentcore deploy` runs. On Runtime the agent's tools always go through the Gateway, since only the Gateway can reach the context layer, and the runtime's own role signs its requests to the Gateway and the Memory. Its checkpoint pool prepares no statements, so it works through the transaction pooler.
- The app's setting `UNDERCOVER_AGENT_RUNTIME`, the runtime's ARN, which the app's role needs permission to invoke. Each request is one attempt, with a new session id of 43 characters, 5 seconds to connect and 20 to read.

### The context layer

- Its package is `context/` without its tests, with the `context` dependency group's packages installed for Linux and Python 3.12. `npm run check:context` imports the server with only that group installed, in a temporary environment.
- Lambda runs the handler `context.server.handler`, behind a Function URL with `AWS_IAM` auth, with no environment variables. It reads files only from its own package and writes none. The handler turns off DNS rebinding protection, since the Function URL's IAM auth guards it.
- Behind the AgentCore Gateway it is the `undercover-context` target, beside the app's `undercover-app`, and the Gateway names each tool `<target>___<operation>`.

### The agent's settings

- `UNDERCOVER_GATEWAY_URL`: the Gateway, when set. The agent then needs the AWS CLI's credentials and region.
- `UNDERCOVER_CONTEXT`: the context layer on the direct route, `http://127.0.0.1:8006/mcp` when unset.
- `UNDERCOVER_MEMORY_ID`: the AgentCore Memory, when set, in the AWS CLI's region and with its credentials.
- The agent reads them when it builds a claim graph, not when it's imported, so `uv run -m agent`, which loads `.env` after its imports, sees them.
