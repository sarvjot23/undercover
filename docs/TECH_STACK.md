# Tech stack

- `backend/`: FastAPI and SQLAlchemy Core, so each query is written once for both databases. It uses Supabase (Postgres) when `DATABASE_URL` is in its environment, in a schema of its own, `undercover`, and otherwise SQLite. `npm run dev` passes `.env`; the tests never do. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. Supabase's free plan allows 15 connections through the session pooler, so each process uses at most 4, and a request waits up to 120 seconds for one rather than fail. At most 8 requests are inside the backend at once (`backend/turns.py`); the rest wait on the event loop, so a swarm can't take every worker thread while the requests holding the connections wait for one.
  - Sign-in: every handler action takes a Supabase access token, which `backend/auth.py` checks with PyJWT's `PyJWKClient` against the project's public keys at `/auth/v1/.well-known/jwks.json` under `VITE_SUPABASE_URL` (read once), with the audience `authenticated`, then finds the handler by the token's email. The project signs with asymmetric keys, so no Supabase secret is needed. The agent's own calls carry `UNDERCOVER_API_KEY` in an `X-API-Key` header, checked in `backend/keys.py` with `secrets.compare_digest` and read from the request rather than with `Header()`, so no API document shows a key input. `agent/client.py` sends it on every call.
  - The agent's own API (`backend/agent_api.py`): `GET /api/agent/openapi.json`, generated with FastAPI's `get_openapi` from the app's routes, filtered to the claim agent's eight operations, with no `servers`, for the AgentCore Gateway.
  - The configuration's versions, the recipe's versions, the settings and the rounds are records the backend owns. Diffs are worked out with Python's `difflib`, and our rule for keeping a version is `backend/verdict.py`.
  - The judge (`backend/judge.py`): Jev, `typesafe/jev-1.13`, through OpenRouter's Decisions endpoint with the `openrouter` package, called only there, at the origin in `JUDGE_URL` (read once; `https://openrouter.ai` by default), with a 10-second timeout and no retries. It runs in the backend, which holds the handlers' reasons, as an evaluation finishes, every claim in parallel.
- `agent/`: our own harness on OpenRouter, in six parts. The improver is a LangChain agent; the rest is our own LangGraph code:
  - The security check (`agent/screening.py`): the claim graph's first node, `check`, a call to GPT-6 Luna at effort `none` with Structured Outputs (`instructions_found` and the reason) through the OpenRouter SDK, on the fields the customer wrote. It isn't part of the versioned configuration.
  - The dispatcher (`agent/dispatcher.py`), a LangGraph graph with no model, as in the Week 2 Day 4 lab: a node lists the run's claims and fans out with one `Send` per claim to a worker node, with `max_concurrency` set to N. It works dispatches and evaluations. The worker calls one function of the harness, `claim.work(claim_id, run)`, and is the only place the dispatcher touches the claim agent. Its `RetryPolicy` waits out LangChain's `ModelRateLimitError` and `ModelTimeoutError`; on the last attempt the worker leaves the claim in progress, which is the `error_handler`'s job, because in LangGraph 1.2.12 an `error_handler` doesn't stop the error while other `Send` tasks run beside it. It saves no progress of its own.
  - The claim agent, a hand-written LangGraph graph, works a claim on a thread of its own. Its nodes record each step and each reply's tokens and cost, return refusals to the model and stop at 30 model calls. It pays as a step of the graph, and waits for a sign-off with `interrupt()` when the backend says a claim needs one. `claim.work` carries on a claim in progress or starts a waiting one, lets rate limits and timeouts through to the dispatcher, and times each run of the graph, which ends at a pause for a sign-off.
  - Its progress is saved after every step with LangGraph's synchronous Postgres checkpointer, in the same database, with `durability="sync"`. Each run of the graph gets a saver of its own on the process's shared pool of 4 connections, because a saver holds a lock around every read and write.
  - The agent's service, a small web service and the agent's entry point, on `UNDERCOVER_AGENT` or `http://127.0.0.1:8002`. It starts dispatches and evaluations, one at a time, refusing a second with a 409, and resumes claims after a sign-off. When it starts, it marks a dispatch or evaluation left running as stopped. The backend calls it through `backend/agent_service.py`.
  - Tracing: each claim's work is one Langfuse session, named after its thread, tagged with its run, such as `dispatch-12`, and its round, such as `round-3`. The improver's work in a round is one session, named after the round's thread.
  - The improver (`agent/improver.py`): a LangChain `create_agent` on GPT-6 Luna at medium reasoning effort, with parallel tool calls turned off and at most 20 model calls a round, the lab's four tools, `HumanInTheLoopMiddleware` on its two proposals and a `PostgresSaver` of its own, on a new thread for each round. The service works a round in `agent/rounds.py`: its evaluations through the dispatcher in this process, each in a fresh `contextvars.Context`. A round's stretch of work holds the service's one-at-a-time lock, so its evaluations are part of it.

  The claim agent reaches claims, documents and its configuration only through the backend's API, with `agent/client.py`; the improver reaches its round, its results and its spending through `agent/improver_client.py`. Each run is built from a version of the configuration: its model and reasoning effort (`default` sets none), or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort set. With `MODEL_NAME` set, that model is the only one allowed, the improver uses it too, and the judge isn't called.
- `dashboard/`: React, Vite and TypeScript. Handlers sign in with `@supabase/supabase-js` and `signInWithPassword`, reading `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, only in `dashboard/src/auth.ts`. Vite reads the repo's `.env` for `npm run dev` only; the unit and end-to-end tests set their own values. The appearance, light, dark or as the computer is, is kept in the browser and set as `data-theme` on the page. Charts are SVG, with no chart library.
- `e2e/`: Playwright tests, with stand-ins for the agent's service, Supabase Auth and the judge.
- `data/`: the business data the backend starts from: `company.json` gives the approval limit its first value, `settings.json` the improvement settings, and `models.json` the models the claim agent may use, with their reasoning efforts and prices per million tokens. `data/evals/` holds the answer key: seeding stores the held-out claims and the handlers' decisions, with their reasons and references, in tables of their own, which no claim operation reads. Only the scoring of an evaluation, the judge and the improver's view use them, and the improver's view holds nothing of the held-out set but its scores. The claim agent never sees them.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. In `.env`: `OPENROUTER_API_KEY`, `DATABASE_URL` (the Supabase session pooler string), `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`, `HANDLER_PASSWORD`, the handlers' password for the browser checks, and `UNDERCOVER_API_KEY`, the agent's API key, made with `secrets.token_urlsafe(32)`.

## Deployment

The backend and the dashboard go to AWS Lambda as one package behind a Function URL, with the database on Supabase. The same app also runs as an ordinary web server.

- `npm run build` builds the dashboard into `dashboard/dist`, with `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` built in, read from `.env` when there is one and otherwise from the environment.
- When `dashboard/dist` exists, the backend serves it at `/` (`backend/static.py`): its files at their own paths, and `index.html` for any other path outside `/api/`. Without it, the backend serves only the API, as with `npm run dev`.
- The package holds `backend/`, `data/` and `dashboard/dist/`, with the packages of the `server` dependency group in `pyproject.toml`, installed for Linux and Python 3.12. At run time the backend imports nothing from outside the package, reads only its own files and writes none. `npm run check:server` imports the backend with only that group installed, in a temporary environment.
- Lambda runs the handler `backend.main.handler`, Mangum with the startup hook off, so nothing seeds the database. A web server runs `backend.main:app`.
- The function's environment is `DATABASE_URL` (Supabase's transaction pooler, on port 6543), `VITE_SUPABASE_URL` and `UNDERCOVER_API_KEY`. Everything else the backend reads has a default, or is needed only by work that can't start without the agent's service, which stays on the laptop.
- When `AWS_LAMBDA_FUNCTION_NAME` is set, as Lambda sets it, the backend opens a database connection for each request and keeps none (`NullPool`), with prepared statements off (`prepare_threshold=None`), since each copy of the function handles one request at a time and the transaction pooler can't prepare statements.
